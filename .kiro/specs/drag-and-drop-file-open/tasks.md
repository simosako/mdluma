# Implementation Plan

- [x] 1. ドロップ対象の選別規則と追加起動の共通土台を整える
- [x] 1.1 ドロップと起動時で共有するファイル採用上限と分配規則を一貫して扱えるようにする
  - 通常ファイルだけを入力順のまま採用し、フォルダは除外できるようにする。
  - 採用対象は先頭 10 件までに制限し、起動時の複数ファイル処理も同じ上限値を参照するようにする。
  - 完了時には、単一ファイル、複数ファイル、フォルダ混在、フォルダのみのいずれでも、現在ウィンドウ用 0 または 1 件と追加ウィンドウ用残余へ同じ規則で分配される。
  - _Requirements: 2.1, 2.2, 3.1, 3.2, 3.3, 3.4_
- [x] 1.2 追加で開くファイルを既存起動契約のまま 1 件ずつ別ウィンドウへ渡せるようにする
  - 追加ファイルの起動責務を現在ウィンドウ更新から分離し、1 ファイル 1 ウィンドウの契約だけを担う境界として切り出す。
  - 追加ファイルの内容読込やエラー表示は子ウィンドウ側へ委譲し、親ウィンドウ側で重複実行しないようにする。
  - 完了時には、追加採用された各ファイルが既存の単一ファイル起動と同じ扱いで独立インスタンスへ委譲される。
  - _Requirements: 2.1, 2.3_

- [x] 2. 既存ウィンドウでのファイルドロップ入力を受け付けられるようにする
- [x] 2.1 (P) 既存ウィンドウが通常ファイルドロップだけを受理し、受け取った順序のまま実行要求へ渡せるようにする
  - 非ファイル payload は受理せず、ドロップした通常ファイルだけを入力順のまま転送できるようにする。
  - パス列は画面状態へ保持せず、その場の入力として処理要求へ渡すだけにする。
  - 完了時には、1 件でも複数件でも通常ファイルドロップ時だけ実行要求が発行され、ファイル順序が保たれる。
  - _Requirements: 1.1, 2.1, 3.3, 3.4_
  - _Boundary: DropInteractionScript_
- [x] 2.2 (P) ドロップ実行要求を型付きのビューアー操作へ正規化できるようにする
  - 既存の通常オープン要求を壊さずに、新しいドロップ要求だけをパス列付きの操作として識別できるようにする。
  - 文字列パスだけを順序保持で受け取り、以降のアプリケーション層がそのまま扱える入力へ変換する。
  - custom titlebar を持つ既存 window binding からの drop 要求も、通常のオープン要求と同じ処理系へ流せるようにする。
  - 完了時には、未知の要求名は無視され、ドロップ要求だけが順序付きパス列として後続処理へ届く。
  - _Requirements: 1.1, 2.1_
  - _Boundary: SciterDropCommandBridge_
- [x] 2.3 現在ウィンドウのドロップ結果を既存の文書表示とエラー表示へ合流させる
  - 採用された先頭 1 件がある場合だけ、現在ウィンドウの表示を既存のファイルオープン経路で置き換えられるようにする。
  - 読み取り失敗や UTF-8 解釈失敗は、新しい専用表示を増やさず既存のユーザー向けエラー表示へ流す。
  - 完了時には、文書表示中でもエラー表示中でも、ドロップした先頭ファイルの成功結果または失敗結果が現在ウィンドウへ反映され、採用ファイルが 0 件なら表示は変化しない。
  - _Depends: 1.1, 2.2_
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 3.4_

- [x] 3. ドロップ計画と追加起動を既存の起動フローへ統合する
- [x] 3.1 既存の複数ファイル起動とドロップ後の追加起動が同じ子ウィンドウ起動契約を共有するようにする
  - 起動時の複数ファイル処理とドロップ後の追加起動が、同じ 1 ファイル 1 ウィンドウの起動境界を再利用するようにする。
  - 親ウィンドウ側では追加ファイルを開き直さず、追加分は共通の起動委譲だけを行うようにする。
  - 完了時には、起動時の複数ファイル処理とドロップ後の追加ファイル処理が同じ追加起動契約へ集約される。
  - _Depends: 1.2_
  - _Requirements: 2.1, 2.3_
- [x] 3.2 先頭 1 件を現在ウィンドウへ、残りを追加ウィンドウへ分岐する一連のドロップ実行を完成させる
  - ドロップされたファイル群から作った分配結果に従い、現在ウィンドウ更新と追加起動を同じ操作の中で順に実行できるようにする。
  - 現在ウィンドウは常に 0 または 1 文書のままに保ち、2 件目以降を同一ウィンドウへ混在表示しないようにする。
  - 先頭 current の読込失敗や UTF-8 失敗があっても、追加対象があれば child 起動委譲は継続するようにする。
  - 完了時には、2-10 件の通常ファイルドロップで先頭 1 件だけが現在ウィンドウへ表示され、残りは各 1 件ずつ別ウィンドウへ委譲され、開けない追加ファイルがあっても他のファイルの起動は継続する。
  - _Depends: 1.1, 2.3, 3.1_
  - _Requirements: 2.1, 2.2, 2.3, 3.1, 3.2, 3.3, 3.4_

- [x] 4. ドロップオープン全体の回帰を自動テストで固定する
- [x] 4.1 (P) 共有分配規則の単体回帰を自動テストで固定する
  - 11 件以上、ファイルとフォルダの混在、フォルダのみ、入力順保持の代表ケースを再現できるようにする。
  - ドロップ経路と起動時経路が同じ上限値と分配規則に従うことを確認する。
  - 完了時には、採用件数制限とフォルダ除外の規則が単体テストで可視化される。
  - _Depends: 1.1_
  - _Requirements: 2.1, 2.2, 3.1, 3.2, 3.3, 3.4_
  - _Boundary: OpenPathsPolicy_
- [x] 4.2 (P) UI のドロップ受理条件と入力順保持を自動テストで固定する
  - 通常ファイル 1 件、複数件、非ファイル payload の代表ケースを再現できるようにする。
  - 実行要求に渡る件数と順序が崩れず、対象外入力では要求が発行されないことを確認する。
  - 完了時には、ドロップ受理境界の入力契約が回帰テストで可視化される。
  - _Depends: 2.1_
  - _Requirements: 1.1, 2.1, 3.3, 3.4_
  - _Boundary: DropInteractionScript_
- [x] 4.3 ドロップ要求のデコードと custom titlebar 付きウィンドウからの到達を自動テストで固定する
  - 既知のドロップ要求、未知の要求名、複数パスの順序保持を再現できるようにする。
  - custom titlebar を持つ既存ウィンドウ binding でも、ドロップ要求が通常のオープン要求と同じ処理系へ届くことを確認する。
  - 完了時には、ドロップ要求の受け口とウィンドウ binding の接続が回帰テストで追える。
  - _Depends: 2.2_
  - _Requirements: 1.1, 2.1_
- [x] 4.4 ドロップ後の現在ウィンドウ置換と追加ウィンドウ起動継続を統合テストで固定する
  - 先頭ファイルの表示置換、読み取り失敗、UTF-8 失敗、フォルダのみ no-op、複数ファイル時の追加起動継続を再現できるようにする。
  - 先頭 10 件制限、1 ウィンドウ 1 文書の維持、一部の追加ファイルが開けなくても他のファイル起動を継続することを確認する。
  - 完了時には、ドロップオープンの主要分岐が統合テストで可視化され、要求 1-3 の回帰が一通り検出できる。
  - _Depends: 3.2_
  - _Requirements: 1.2, 1.3, 1.4, 2.1, 2.2, 2.3, 3.1, 3.2, 3.3, 3.4_
