# Review Notes - 2026-05-08

この文書は、2026-05-08 時点のコードレビューで挙がった項目のうち、すでに対応済みのもの、および今回は対応しないと判断したものを除外して整理したものです。

目的は、今後の修正方針を検討しやすくすることです。各項目は、MDLuma の方針である軽量・高速起動・省メモリ・最小構成を前提に、効果とリスクを見ながら小さく進める想定です。

## 優先度の高い候補

### 1. `ensure_local_only()` の毎回検査を削減する

対象: `src/html_shell.rs`

`ensure_local_only()` は、埋め込み済みの不変アセットに対して、HTML shell の render ごとに lowercase コピーと検索を行っています。

この検査は安全性の意図がありますが、対象がビルド時に固定されるアセットであるため、毎回実行する必要性は低いです。起動や表示更新の軽さを重視するなら、次のどちらかを検討できます。

- 初回のみ検査する。
- テストで安全性を保証し、実行時検査を削る。

注意点として、実行時検査を削る場合は、将来アセット内容が変わったときに危険な外部 URL が混入しないよう、テストで十分にカバーする必要があります。

### 2. `open_url_in_browser()` に URL scheme の二重防御を追加する

対象: `src/platform/windows_browser.rs`

`open_url_in_browser()` は、現状では呼び出し元で URL scheme を検証している前提です。そのため、通常の経路では `http` / `https` のみが渡る想定です。

ただし、関数境界でも `http` / `https` のみ許可するようにしておくと、将来別の呼び出し元が追加された場合の防御になります。

修正する場合は、既存の呼び出し元検証を置き換えるのではなく、低コストな二重防御として追加するのがよいです。ユーザー向け挙動を変えないよう、既存のエラー処理やメッセージとの整合も確認してください。

### 3. `apply_body_font()` の JS 文字列生成を堅牢化する

対象: `src/sciter/window.rs`

`apply_body_font()` は、フォント名を JavaScript 文字列に埋め込んでいます。現状でも `"` と `\` はエスケープされていますが、JavaScript 文字列を手作業で組み立てる処理は壊れやすいです。

より堅牢にするには、JSON 文字列生成に近い処理へ寄せる、または既存の安全な文字列エスケープ処理があればそれを共用する方針が考えられます。

この変更では Sciter.js の挙動に注意が必要です。ブラウザ前提の DOM や JS 実行モデルを想定せず、既存の Sciter SDK ドキュメントやサンプルに沿って確認してください。

## 構造・責務の整理候補

### 4. `AppController` の型パラメータと初期化処理を整理する

対象: `src/app.rs`

`AppController<D, F, L, R, H, U, S, E>` は型パラメータが多く、実装ブロックやコンストラクタの見通しを悪くしています。

また、複数のコンストラクタで設定読み込みとフィールド初期化が重複しています。今後の変更時に初期化手順の差異が生まれやすいため、共通化の余地があります。

ただし、過度な抽象化は MDLuma のシンプルさを損なう可能性があります。対応する場合は、次のような小さい変更から始めるのが安全です。

- フィールド初期化の共通部分だけを private helper に寄せる。
- 型パラメータを大きく減らすより先に、コンストラクタ重複を減らす。
- テストしやすさを維持し、trait object 化や大きな DI コンテナ化は避ける。

### 5. `prepare_startup_path()` と `open_selected_path()` の処理重複を整理する

対象: `src/app.rs`

`prepare_startup_path()` と `open_selected_path()` には、概ね `load -> render -> recent file 記録` の流れが重複しています。

この重複は、将来レンダリング前後の処理やエラー処理を変更するときに片方だけ修正されるリスクがあります。

対応する場合は、ファイル読み込みから表示準備までの共通処理を小さな private method に切り出す程度がよいです。ユーザー操作起点と起動時処理でエラー表示や recent file 更新条件が異なる可能性があるため、完全に一体化しすぎないよう注意してください。

### 6. 大きくなった `src/app.rs` のテストを整理する

対象: `src/app.rs`

`src/app.rs` は本体よりテストコードがかなり大きくなっており、ナビゲーション性が悪くなっています。

対応する場合は、まず共通テストユーティリティを切り出し、テストの意図を読みやすくするのがよいです。大きなテスト分割を急ぐより、重複している fixture や recorder を整理する方がリスクが低いです。

### 7. 共通テストユーティリティを追加する

対象候補: `src/test_util.rs` または既存のテスト補助 module

`TestDir` やモック / 記録用 launcher のような補助コードが、複数ファイルに重複しています。

共通化すると、テスト追加時のコストを下げられます。ただし、テストユーティリティを過度に汎用化すると、各テストの前提が見えにくくなります。

対応する場合は、明確に重複しているものだけを小さく移動し、テストごとの個別条件は各テスト内に残す方針が適しています。

## 小さな整理候補

### 8. `MarkdownOptions` の必要性を見直す

対象: `src/markdown.rs`

`MarkdownOptions` は現状では空 struct です。将来オプションを増やす予定が具体的にないなら、単なる関数引数や既定処理で足りる可能性があります。

一方で、今後 Markdown 変換オプションを増やす見込みがあるなら残しても構いません。判断基準は、近い将来に具体的なオプション追加があるかどうかです。

### 9. `ResourcePolicy` の single-variant enum を見直す

対象: `src/html_sanitizer.rs`

`ResourcePolicy` は現状 `LocalOnly` のみを持つ single-variant enum です。将来別ポリシーを追加する予定がないなら、enum として持つ必要は薄いです。

ただし、HTML サニタイズ処理では「リソース URL をどの基準で許可するか」という概念自体は重要です。削る場合も、ポリシーの意図がコードから失われないよう、関数名やテスト名で補うとよいです。

### 10. `MAX_OPEN_FILE_COUNT` の配置と名前を見直す

対象: `src/open_paths.rs`, `src/startup_args.rs`

`MAX_OPEN_FILE_COUNT` は `open_paths.rs` と `startup_args.rs` の両方で共有されています。実質的にはアプリ全体の「同時に開くファイル数上限」という共通ポリシーですが、現在の配置や名前からはその性質が少し分かりにくいです。

対応する場合は、共通ポリシーであることが分かる場所へ移す、または名前をより具体化する案があります。

ただし、影響は小さいため、他の修正と同時に触る程度で十分です。

## セキュリティ強化候補

### 11. 外部エディタパスの検証を追加する

対象: `src/external_editor.rs`

外部エディタ起動では、設定されたエディタパスを `Command::new()` に渡しています。設定ファイルが改ざんされている場合、意図しない実行ファイルを起動するリスクがあります。

これはローカル設定ファイル改ざんを前提にしたリスクであり、通常の Markdown 表示経路より優先度は低めです。ただし、次のような軽い検証は検討できます。

- パスが存在することを確認する。
- 通常ファイルであることを確認する。
- Windows では想定される実行形式か確認する。

注意点として、外部エディタには `.exe` 以外の起動形態や PATH 解決を使いたいユーザーもいる可能性があります。制限を強くしすぎると利便性を損なうため、現行仕様との整合を先に確認してください。

## 省メモリ・起動速度の検討候補

### 12. 文書更新時の HTML 全体再ロードを見直す

対象: `src/sciter/window.rs`

文書更新時に HTML 全体を再ロードしているため、JS や CSS も再パースされます。差分更新にできればコスト削減の余地があります。

一方で、全体再ロードには Sciter 側の状態を明確にリセットできる利点があります。差分更新にすると、状態残りやイベント再登録などの問題が出る可能性があります。

そのため、この項目はすぐに実装するより、実測でボトルネックになっている場合に検討するのがよいです。

### 13. deferred load の HTML 複製を見直す

対象: `src/sciter/ffi.rs`

deferred load では HTML 全体を `to_string()` で複製しています。メモリ削減の余地はありますが、Sciter FFI と lifetime が絡むため、安易に変更すると unsafe 周辺のリスクが上がります。

優先度は低めです。対応する場合は、Sciter 側がいつまでバッファを参照するかをヘッダや SDK サンプルで確認し、テストだけでなく実機動作も確認してください。

### 14. 巨大 Markdown ファイルへの扱いを検討する

対象: `src/document.rs`

現在は Markdown ファイル全体をメモリに読み込んでいます。Comrak が `&str` 入力であるため、根本的にストリーミング処理へ変えるのは難しいです。

現実的な対応としては、巨大ファイルに対する上限や警告を検討する程度です。ただし、上限を設ける場合はユーザー体験に直接影響するため、実際に問題が出てから判断しても遅くありません。

## 推奨する進め方

次に着手するなら、リスクが低く効果が分かりやすい順に進めるのがよいです。

1. `ensure_local_only()` の毎回検査を削減する。
2. `open_url_in_browser()` に scheme の二重防御を追加する。
3. `apply_body_font()` の JS 文字列生成を堅牢化する。
4. `AppController` のコンストラクタ重複と load/render 重複を小さく整理する。
5. `MarkdownOptions` / `ResourcePolicy` / `MAX_OPEN_FILE_COUNT` の小さな整理を行う。

大きな構造変更や Sciter 更新方式の変更は、軽量性や安全性を損なわないよう、実測または具体的な不具合が出てから進めるのが安全です。
